# M159 code health follow-ups

Tasks found by reviewing upstream changes in `158.0.8127.2..159.0.8148.0` (10794
commits) for regressions, deprecations and code-health migrations that apply to
Brave. Tick items off as they land.

## 1. Regressions

### Brave's page action chips lose to every other chip

[a28169e8f1a1](https://chromium.googlesource.com/chromium/src/+/a28169e8f1a188a4e04bd8bd91415a7f025aaad9)
enables `kPageActionsPrioritySelector` by default, so `CreateChipSelector()`
returns `PriorityChipSelector`. It shows only chips above the active priority
(below `kSecurityTrustAndPermissions`), and a higher one hides the rest. Brave's
entries in
`patches/chrome-browser-ui-page_action-page_action_properties_provider.cc.patch`
set no `.priority`, so they get `kUnknown`, the lowest: the onion location and
partitioned storage chips are suppressed by any upstream chip, and by each
other.

- [ ] Give `kActionShowOnionLocation` and `kActionShowPartitionedStorage` a
      `.priority` in the patch (or pass one in the `SuggestionChipConfig` at
      `browser/ui/views/page_action/onion_location_page_action_controller.cc:143`
      and `partitioned_storage_page_action_controller.cc:199`)
- [ ] Decide priorities for the patch's other Brave entries (PSST, Speedreader,
      Wayback Machine, Playlist, Brave News) in case they show chips
- [ ] Test a Brave chip shown next to a competing upstream chip, e.g. in
      `browser/ui/views/page_action/onion_location_page_action_controller_unittest.cc`

### Shutdown DCHECK after memory pressure: async memory consumers on `BLOCK_SHUTDOWN` sequences

"[cr159][Ads][Rewards] Move the databases to `base::MemoryConsumer`" (culprit
[34431f87c812](https://chromium.googlesource.com/chromium/src/+/34431f87c812c3c38e04d06b4ec5e872288112f6))
registers the Ads and Rewards databases with
`base::AsyncMemoryConsumerRegistration` from `BLOCK_SHUTDOWN` sequences. Both
are destroyed there only once the main loop has quit: Ads' `Database`
(in-process, `database_manager.cc:32-35`) during
`BrowserMainLoop::ShutdownThreadsAndCleanUp`, Rewards' self-owned
`RewardsDatabase` (`rewards_service_impl.cc:229-231`) after profile teardown.
`~AsyncMemoryConsumerRegistration` sets `async_handle_destroyed_` and
`DeleteSoon`s its `MainThread` to the main thread, which never runs it, so the
`MainThread` stays registered. `~BrowserMemoryCoordinatorImpl` (owned by
`ContentMainRunnerImpl`, after the thread pool's shutdown) destroys
`memory_pressure_listener_policy_registration_` before `registry_`, and the
policy's removal notifies every consumer still registered.
`MainThread::OnUpdateMemoryLimit` doesn't check `async_handle_destroyed_`, and
posts to the dead sequence: `DCHECK failed: !shutdown_event_->IsSignaled()` in
`TaskTracker::WillPostTask`. Only `BLOCK_SHUTDOWN` sequences DCHECK; other
sequences drop the post silently, which is why upstream's leaked `MainThread`s
(`BlobMemoryController`, `SharedBlockCaches`) don't fail. Release builds have no
DCHECK, and the task never runs.

Verified in `AutocompleteDictionaryPreloadBrowserTest.*MemoryPressure` with gdb
on a `--single-process-tests` run: the browser process registers
`BlobMemoryController`, `SharedBlockCaches` and `AdsDatabase`, and the DCHECK
follows `AdsDatabase`'s notification. Rewards doesn't start in a fresh profile;
it hits the same path once its engine has run and a policy has lowered the
limit. The leak dates from
[003ead1d49ab](https://chromium.googlesource.com/chromium/src/+/003ead1d49ab9485cf30d4d1b013cb07510fd221)
(`DeleteSoon` for async registrations).

- [x] Skip `MainThread::OnUpdateMemoryLimit()` and `OnReleaseMemory()` once
      `async_handle_destroyed_` is set, with a plaster on
      `base/memory_coordinator/async_memory_consumer_registration.cc` (fixed in
      ``[cr159][Ads][Rewards] Move the databases to `base::MemoryConsumer` ``)
- [x] Drop the `AutocompleteDictionaryPreloadBrowserTest` entries from
      `test/filters/browser_tests.filter` (fixed in
      `[cr159] Disable failing upstream tests.`)
- [ ] Send the fix upstream (with a test in
