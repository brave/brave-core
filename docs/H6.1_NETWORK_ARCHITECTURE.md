# H6.1 現行 Chromium 網路架構調研：原生 `bnes://` 協定註冊

> **用途**：H6 軌道設計備查。僅供未來的 C++ 原生攔截實作參考，不代替可重複現的編譯證據。  
> **範圍**：Chromium 151（對應 brave-core 1.95.44）Windows 桌機版；禁止假設已淘汰 API。  
> **對照**：`implementation_plan.md` §九.3 H6.1；`進度報表.md` §七 H6.1。

---

## 1. 結論摘要

Chromium 現代網路棧處理 custom scheme 的**正確入口**是 `URLLoaderFactory` 子類化，而非已淘汰的 `URLRequestJob` / `ProtocolHandler` 推測。`bnes://` 需在**三個層面**完成註冊：

1. **Scheme registry**：告诉 Chromium `bnes` 是一個已知 scheme，並指定其安全語義（secure、display-isolated、不允許 javascript: 等）。
2. **URLLoaderFactory 子類**：實際處理 `bnes://` 導航，回傳 IPFS content stream 或錯誤。
3. **上游最小觸點**：在 Brave/Chromium 既有檔案中僅增加 `// [BNES]` 標示的引入與註冊。

---

## 2. 現代 Chromium Custom Scheme 架構

### 2.1 URLLoaderFactory 子類化（正確做法）

Chromium 不再使用 `URLRequestJob` / `ProtocolHandler` 做為 custom scheme 的擴展點。正確模式見 `text/plain`（2022-01-21）與 Chromium 源碼：

- **`AboutURLLoaderFactory`**：處理 `about://`
- **`DataURLLoaderFactory`**：處理 `data://`
- **`BlobURLLoaderFactory`**：處理 `blob://`

所有 custom scheme loader 都 subclass `network::SelfDeletingURLLoaderFactory`，透過 Mojo `PendingRemote` 注入網路服務。

**我們的正確認計**：`BnesURLLoaderFactory`，subclass `network::SelfDeletingURLLoaderFactory`，在 `CreateLoader()` 中：
1. 驗證 URL 通過 `bnes::IsAllowedNavigationUrl()`
2. 解析 host → CID（透過內建 MetaMask 或直連 RPC）
3. 建立 `URLLoader` 回傳 IPFS gateway HTTPS stream

### 2.2 Scheme Registry 行為列表

Chromium 沒有類似 IE `IInternetProtocolInfo` 的查詢介面；每個 scheme 必須**手動加入** Chromium 原始碼中硬編碼的行為列表。核心檔案：

| 行為 | 函數/巨集 | 說明 |
|------|-----------|------|
| Secure context | `RegisterURLSchemeAsSecure` | 允許在 HTTPS 頁面使用、啟用 WebCrypto 等 Secure Context API |
| 不允許 javascript: | `RegisterURLSchemeAsNotAllowingJavascriptURLs` | 禁止書籤列/omnibox 的 `javascript:` 注入 |
| Display isolated | `RegisterURLSchemeAsDisplayIsolated` | 跨 origin 不得 iframe/hyperlink 至此 scheme |
| 可加入歷史記錄 | `CanAddURLToHistory` | 控制 navigation 是否寫入 history |
| Handled protocol | `IsHandledProtocol` | 讓瀏覽器知道此 scheme 有原生處理器 |
| 不允許巢狀 | `RegisterURLSchemeAsNotForwardingToDifferentScheme` | 防止 `bnes://...` 被轉向其他 scheme |

## 3. Brave Wiki 的實際經驗

Brave 在 `brave/brave-browser/wiki/Adding-a-protocol-scheme-to-Brave` 中記錄了新增 protocol scheme 的實際步驟（2020-04-24，仍適用 brave-core 1.95.44）：

| Brave 函數 | 用途 | 我們的應用 |
|------------|------|------------|
| `AddAdditionalSchemes` | 將 scheme 加入與 `chrome://` 同級別的列表 | **不需要**：`bnes://` 不是 `chrome://` alias |
| `GrantRequestScheme` | 允許 WebUI 存取 | **不需要**：BNES 不是 WebUI |
| `RegisterURLSchemeAsNotAllowingJavascriptURLs` | 禁止 `javascript:` 書籤注入 | **需要** |
| `RegisterURLSchemeAsDisplayIsolated` | 跨 origin 隔離 | **需要** |
| `CanAddURLToHistory` | 控制 history 寫入 | **可選**：`bnes://` 導航可寫入 history |
| `IsHandledProtocol` | 標記為有原生處理器 | **需要** |
| `ExtensionTabUtil::IsKillURL` | 僅用於 `brave://` = `chrome://` alias | **不需要** |

## 4. 上游最小觸點清單（插入式分叉原則）

根據 `implementation_plan.md` §4.3「上游觸點最小化原則」，僅允許以下最小量修改：

| # | 上游檔案 | 觸點內容 | `// [BNES]` 註解 |
|---|----------|----------|-----------------|
| 1 | `content/public/common/url_constants.cc`（或 brave-core 對應 patch） | 將 `"bnes"` 加入 secure scheme 列表 | ✅ |
| 2 | `content/public/browser/content_browser_client.cc`（或 brave-core patch） | 在 `GetURLDataManagerFactory()` 或類似 hook 中注入 `BnesURLLoaderFactory` | ✅ |
| 3 | `url/url_util.cc`（或 brave-core patch） | 註冊 `bnes` scheme 的行為：secure、display-isolated、not-allowing-javascript、handled | ✅ |
| 4 | `browser/ui/browser_commands.cc`（brave-core patch） | 引入 BNS 設定頁面入口 | ✅ |

**注意**：Brave overlay 通常透過 `brave-core/patches/` 目錄下的 `.patch` 檔案或 `chromium_src/` 覆寫來實現這些觸點，而非直接修改 `C:\chromium\src\chromium\` 內容。這與我們的插入式分叉原則一致。

## 5. 安全邊界對齊

以下規則必須與 `bns/src/utils/bnsSecurity.ts`（TS）、`metamask-extension/shared/bns/`（錢包）和 C++（本文件）**三端一致**：

| 規則 | C++（`bnes/bns_security.cc`） | TS（`bnsSecurity.ts`） | 錢包（`shared/bns`） |
|------|------------------------------|----------------------|---------------------|
| `.bnes` host label | `IsAllowedNavigationUrl()` | `normalizeBnesName()` | `validateBnesName()` |
| CID 格式 | `IsValidCid()` | `normalizeCid()` | `validateCid()` |
| Gateway origin pin | `IsAllowedGatewayUrl()` | `resolveBnesContent()` | `resolveBnesContent()` |
| SSRF 拒絕 | `IsPublicNetworkAddress()` | N/A（前端無 IP 解析） | N/A |
| Secure context | 需註冊為 secure scheme | N/A（前端 inherit） | N/A |

## 6. 實作順序建議

1. **先註冊 scheme 行為**（`url_util.cc` patch）：讓瀏覽器認識 `bnes://` 為 secure、display-isolated。
2. **再注入 URLLoaderFactory**（`content_browser_client.cc` patch）：實際攔截導航。
3. **實作 `BnesURLLoaderFactory`**（`brave/bnes/` 獨立目錄）：解析 → RPC/quorum → CID → gateway stream。
4. **最後做 browser test**（H6.5）：驗證 `bnes://test.bnes` 可載入、網址列不跳轉、Secure Context 可用。
